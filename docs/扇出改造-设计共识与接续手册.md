## 1. 项目目标与边界

### 1.1 目标

```text
提问 → 检索 key* 槽 → 并行/多路径推理
  → 每条路径可回溯：前提段落、结论、步骤
  → 监督层在工具/网关边界记账（非完整 ReAct）
```

### 1.2 边界（已共识）

| 是 | 不是 |
|----|------|
| key\* 注入监督层；模型只能「写信」，执行必须过**网关** | 裸 LLM ReAct 循环 |
| 宏 loop：HarnessContext 编译器 + 写信台多轮 + 网关批量 | 单次 chat 堆叠 |
| 生成可能路径 + 前提可定位 + 人事后采纳 | 零幻觉承诺 |
| DSH 适合作执行壳；docuverse dev 保留书槽/绿框/写信台/扇出 UI | 二选一废弃 dev |
| 默认载体 = 身份坐标 + 已结算效果 | 聊天记录堆叠 / 全书塞进 prompt |

- **不要**把本库改动推回原库 `diergbanben-`（见 `FORK.md`）。

### 1.3 模型锁死（已钉）

| 用途 | 模型 |
|------|------|
| 主推理 / infer | **DeepSeek-V4-Flash** |
| 向量嵌入 | **Qwen3-VL-Embedding** |

换模型会改变 fingerprint；reuse 不得跨模型误命中旧结论。

### 1.4 采纳边界（已钉）

| 动作 | 效果 |
|------|------|
| **accept / 采纳** | 铸资产并回流（可按身份跳回页上绿框；可供后续 reuse） |
| **未采纳** | **默认不进永久记忆**；本轮可并列展示，但不该当成已回流资产混进下一轮「新路径」 |

## 2. 核心身份类型（A / B / C）

### 2.1 类型 A：`key*`（分析对象）

- OCR/排放铸键；效果 = bbox + `faces`（文字脸 T / 图脸 fig）。
- 人读 = 绿框；机读 = T（`facesToReadout`）。
- 门牌公式（密封句柄）：`h1.*`（服务端 `protocolMintKey` / `emit-page`）。
- **身份稳定**：语义标题、节名**不得**写进 key 公式；展示用别名/编译 prompt。

### 2.2 类型 B：加工与路径身份

| ID | 含义 | 典型位置 |
|----|------|----------|
| `actionId` | 网关一步动作存档 | `toolGateway.ts` |
| `directionId` | 结论资产 `dir_${actionId}` | infer / reuse 后 |
| `pathId` | 扇出 UI 路径行 `path_${actionId}` | `fanoutRunner.ts` |

- **输入**靠 `premiseKeys` + excerpt，不是 actionId。
- 同一次 infer 串起 actionId / directionId / pathId。
- reuse 也盖新 `actionId`（审计「本轮走了复用」），结论可复用旧 directionId。

### 2.3 类型 C（待落地）：语义出处

- `SectionNode`：节树（章/节/小节/主题块）。
- `SlotProvenance`：每个 `key*` → 属于哪一节（主归属 + 可选次归属）。
- **不是** compose 候选袋；是建库/编目后的**稳定语义地图**。

## 3. 三层存储：字典 vs 注意力

```text
┌─────────────────────────────────────────┐
│ 书域字典（冷存储，按 docId，类似外挂 KV）   │
│  · BookIndex：key* → T, bbox, ord, vBook │
│  · BookSemanticIndex：节树 + SlotProvenance │
│  默认不进 prompt                         │
└─────────────────┬───────────────────────┘
                  │ Harness 编译器按策略抽取
                  ▼
┌─────────────────────────────────────────┐
│ Working Context / HarnessContext         │
│  本轮问句 + excerpt/blocks + pathMarker  │
│  + expandedKeys / collapsed 指针         │
│  = 实际送进主推理模型的注意力投影          │
└─────────────────────────────────────────┘
```

| 存储 | 角色 |
|------|------|
| **BookIndex** | 物理原子表：门牌 → 领土（T 全文存 `excerpt`/`faces`，不是摘要） |
| **BookSemanticIndex** | 语义家谱：门牌 → 属于哪一节、节在讲啥 |
| **compose 候选袋** | 每轮问句下的动态推理配方（fine/window/cluster/cross） |
| **Working Context** | 本轮 prompt 真包含什么 |

**形式化上下文** = harness 已盖章执行的投影（ActionRecord 表），不是聊天记录堆叠。

### 3.1 轻量原则：默认不搬原材料

相对普通 agent 上下文，本库更轻，不是因为摘要魔法，而是默认协议是 **「坐标表 + 结算效果」**：

| 层级 | 普通 agent | 本库坐标上下文 |
|------|------------|----------------|
| 原材料 | 常整段留在 thread | A 槽 T 只在字典里，**默认不进 prompt** |
| 加工结果 | 散文结论混在聊天里 | B 路径：`pathMarker` + `ops` + 结论（机读） |
| 复用 | 再跑一遍或靠摘要猜 | 指纹命中 → 只带 `pathId` + 结论 |
| 增长方式 | 对话线性变长 | **表状增长**：多一行路径，不是多粘一万字 |

**三层「不展开」：**

```text
1. 对象层：memberKeys 签名 —— 「这袋是什么」一行句柄
2. 路径层：pathMarker / ops —— 「怎么推的」不重复散文
3. 结算层：reuse —— 「推过了」连路径都可只带指纹
```

原材料不是删掉，而是**沉到 BookIndex**；上下文只留引用 + 当前步需要的展开片（按需 FAULT_IN / expand）。

### 3.2 已结算 / 未结算（settled / pending）

与 collapsed/expanded **同一思想**，换了说法：

| | 含义 | 进下一轮 prompt |
|--|------|-----------------|
| **已结算（settled）** | 执行已盖章：身份号 + 结论/配方 | **只认号**，不展开 T |
| **未结算（pending）** | 尚准许新跑 / 需核对原文 | 才展开对应木块 T，交网关 |

记忆 = 「哪些执行已经盖章、哪些还准许发生」，不是聊天记录。

## 4. collapsed / expanded / reuse / deferred

### 4.1 定义（按 key\*，非按「历史 vs 当前」简单二分）

| 状态 | 含义 |
|------|------|
| **collapsed** | 当前任务注意力里**只认号**（pathMarker、前提名单、draftKeys），prompt **无**该槽全文 T |
| **expanded** | 本轮工作上下文里**已有**该槽 T；下轮可只留指针不重复粘字 |
| **未引用** | 不在 Working Context（全书字典里仍有） |

对照 §3.2：已结算路径上的前提 key 通常表现为 **collapsed**；本轮 expand/FAULT_IN 打开的才是 **expanded**。

### 4.2 写信台三态（per 推理单元 / 袋）

| decision | 本轮行为 | memberKeys 的 T |
|----------|----------|-----------------|
| **expand** | 网关 infer | **现状**：整袋 excerpt 一次全开 → 袋内 key 均 expanded |
| **reuse** | 网关短路，不调主模型 | **collapsed**；上下文里是 pathMarker + 旧 conclusion/path，**不是 excerpt** |
| **deferred** | 本轮不做 | collapsed；桌上知道有，通常不算注意力材料 |

### 4.3 常见误解澄清

- **collapsed ≠ 所有未 expand 的 compose 组合**：还包括全书未入选 key、跨轮指针等。
- **expand 行内部（现状）**：没有袋内「A expanded、B collapsed」——整段 excerpt 已含全部 memberKeys。
- **假想微 loop（未实现）**：单次 infer 后若 Validator 判「证据不足」，**不会**自动 FAULT_IN 再 infer；须下轮重新检索→写信→网关。

### 4.4 FAULT_IN（目标设计）

- 按需把某 key 的 T 拉进工作上下文；可整袋可部分；已展开用指针。
- **提议** → 写信台/人批 → **网关**执行；模型不能私自 fetch。
- 「缺」的对象范围：
  - L0：全书 BookIndex（硬上限）
  - L1：当前 docId
  - L2：retrieve + compose 可达前沿
  - L3：当前 infer 单元 AllowedKeys（memberKeys）
  - L4：其中 collapsed 且被判定需要的子集

## 5. 网关工序（已实现）

```text
retrieve  → draftKeys（种子，不注入）
compose   → 候选袋（memberKeys 配方）
写信台    → reuse | expand | deferred（+ expandBudget 策略）
infer     → actionId, dir_*, excerpt, premiseKeys
reuse     → 新 actionId，复用旧 direction/path
pathMarker → infer 后压缩（PATH_MARK v1：Q/C/P/keys）
accept    → 采纳＝铸资产回流（未采纳默认不进永久记忆）
```

### 5.1 工具网关

| 动作 | 文件 | 要点 |
|------|------|------|
| retrieve | `toolGateway.ts` | `premiseKeys` 故意为空；只产 draftKeys |
| compose | `fanoutCompose.ts` + `composePolicy.ts` | fine / window / cluster / cross；由 **ComposePolicy** 勾选 |
| infer | `toolGateway.ts` | 选定≡注入；可选 excerpt 480 字软截断 |
| reuse | `toolArchive.ts` + gateway | memberKeys 签名 + 问句相似度 ≥0.35 + fingerprint |
| 写信台 | `letterDesk.ts` | `proposeLetterRows`；策略 budget/reuse_prefer/… |
| 对照台 | `GatewayFormalizeAbPanel.tsx` | 同袋并行/串行对比「网关一体 ops」vs「事后 formalize」 |

### 5.2 memberKeys vs fingerprint

| | memberKeys | fingerprint |
|--|------------|-------------|
| 问什么 | 袋子里有哪些前提（**对象**） | 用什么方式推的（**过程**） |
| 内容 | 排序后的槽列表签名 | `infer \| 对象签名 \| fine/cluster/cross \| modelId` |
| 同袋换模型 | 签名相同 | 指纹不同 |

### 5.3 expandBudget（策略预算）

- `LetterRunStrategy = budget` 时：本轮最多 N 行 **expand**，其余 **deferred**。
- 是「新 infer 条数」上限，不是 token 预算。

### 5.4 reuse vs expand

| | reuse | expand |
|--|-------|--------|
| 主模型 | 不调 | 调 |
| 模型是否看 T | 否 | 是 |
| 上下文 | pathMarker / 旧结论指针 | excerpt 或 infer-ops blocks |
| 新 actionId | 是（审计） | 是 |

### 5.5 形式化 ops 词表（木块级）

把「前提如何推出结论」译成步骤；**最小单位是木块身份（key\*），不是再拆文本**。

| op | 含义 |
|----|------|
| `attend` | 从 keys 读出可核对的事实/表述 |
| `infer` | 在已 attend 材料上推一步 |
| `combine` | 合并多槽主张 |
| `contrast` | 对比验证 |
| `conclude` | 收束为最终结论（claim 须对齐结论） |

- 代码：`docuverse/src/reasoning/formalPath.ts`（`FormalOpKind`）；校验见 `formalValidator.ts`（`usedKeys ⊆ 袋内 key*`）。
- 对照台：`GatewayFormalizeAbPanel` 用来看 ops 是否真在讲「这些木块如何推出结论」。
- **概率过检，不是数学证明**；同输入必同路径（HoTT）**不是**工程目标。

### 5.6 ComposePolicy（组合策略 · 与 MotionPlan 并列）

**早期下一刀**（打磨写信台组合）与后来的 **MotionPlan**（打开哪些 T）是两层，**不是互相替代**：

| | ComposePolicy | MotionPlan |
|--|---------------|------------|
| 回答 | 本轮枚举哪些**袋配方**（单槽/同页/邻接窗/跨页） | 对候选袋排序：expand / reuse / deferred，以及 faultInKeys |
| 代码 | `composePolicy.ts`；HUD 勾选 | 待落地 `buildMotionPlans` |
| 典型旋钮 | `includeFine` / `includeSamePageCluster` / `includeWindow`（邻接窗）/ `includeCrossPage` + `ord` 阅读序 | score、rationale、reuseFromPathId |

切片太细丢上下文，**不是 rerank 能修的**，而是写信台怎么按 `ComposePolicy` + `ord` 组袋。

## 6. BookSemanticIndex（待落地）

### 6.1 SectionNode（节树）

```typescript
// 草案 — 未入 types.ts
interface SectionNode {
  nodeId: string
  parentId?: string
  kind: 'part' | 'chapter' | 'section' | 'subsection' | 'theme' | 'ai_inferred'
  title: string              // 可读语义，重点不是 p41
  summary?: string
  pageSpan?: [number, number] // 弱锚，对齐 PDF 目录
  // ordSpan 可不要：用 SlotProvenance 反查 key.ord 聚合即可
  source: 'pdf_outline' | 'ocr_heading' | 'ai_inferred' | 'human'
  probe?: number[]           // 节级向量（可选）
}
```

- `source` 不同 = 节标题来源不同（PDF 书签 / OCR 样式 / AI 推断 / 人工），用于审计与排序加权。
- 无目录书：AI 生成节树草案 → 人可改 → 再挂 SlotProvenance。

### 6.2 SlotProvenance（槽出处表）

```typescript
interface SlotProvenance {
  key: string                // key* 外键 → BookIndex
  primaryNodeId: string      // 主归属节
  secondaryNodeIds?: string[]
  role: 'body' | 'heading' | 'caption' | 'figure' | 'footnote' | 'sidebar'
  confidence?: number        // 可选；MVP 可删，自动 loop 时作刹车
  alignedBy: 'outline' | 'heading_match' | 'layout' | 'ai' | 'human'
}
```

**SlotProvenance** = 「每个 key\* 从书的哪块语义结构来」的一行登记表。

### 6.3 语义表 ≠ compose 组合

- **语义家谱** = 稳定地图（运动脑/retrieve 的输入地形）。
- **打开策略（MotionPlan）** = 本轮「开哪些 key 的 T」的多种方案，运动脑排序后给人或 loop。

### 6.4 防 LLM 输错 key

- **后台**：`SlotProvenance` 关系表（`key → nodeId`），好维护、好检索。
- **进 prompt**：编译器按节标题**层级排版**（infer-ops 风格：`### 节标题` + `key:` + `text:`）。
- **不要**把标题写进 key\* 身份；靠 **AllowedKeys 白名单 + formalValidator**（`REJECT_KEY_NOT_ALLOWED`）。
- 参考：`docuverse/api/_lib/protocol/inferOpsCore.ts` 的 blocks 格式。

## 7. 运动脑（Motion Brain）— 设计共识

### 7.1 三个大脑分工

```text
运动脑（Motion Brain）
  输入：问句、节树摘要、draftKeys、compose 袋、workingSet、pathMarker（结构化，短）
  输出：排序后的 MotionPlan[]（faultInKeys、reuse/expand/deferred、rationale）
  不做：拉 T、不写最终结论

编译器（Harness Compiler）
  读字典 → 按节标题拼 blocks → AllowedKeys + 木块 prompt

主推理脑（Infer Brain）
  读编译后 prompt（含 T）→ conclusion / path / usedKeys
```

- 运动脑**可以是 LLM**，但读的是**地图+状态**，不是编译后的长 prompt。
- 也可分层：规则 retrieve/compose/reuse + 向量打分 + LLM 重排。

### 7.2 MotionPlan（打开策略）草案

```typescript
interface MotionPlan {
  rank: number
  planId: string
  action: 'expand' | 'reuse' | 'deferred'
  faultInKeys: string[]       // 要开门的 key*
  unitKey?: string             // 对应 compose 单元
  reuseFromPathId?: string
  score: number
  rationale: string
}
```

### 7.3 宏 loop（可落地）

```text
Round n:
  ① retrieve（语义表缩范围）→ draftKeys
  ② compose → 候选袋
  ③ 运动脑 buildMotionPlans → 排序
  ④ 写信台 / 自动取 top-1 → 定案
  ⑤ 网关：faultInKeys → 从 BookIndex 取 T
  ⑥ 编译器 → infer-ops blocks prompt
  ⑦ 主推理 infer → pathMarker
  ⑧ Validator 够？→ 采纳 : 回到 ③（下一 plan 或补 key）
```

### 7.4 微 loop（未实现）

- 同一次 expand infer 内：Validator 判缺材料 → 自动 FAULT_IN → 再 infer。
- 现状：须用户下轮再提问/再写信。

## 8. 完整工序与表样（编译前后）

### 8.1 建库（一次）

**BookIndex**（物理）

| key* | page | ord | T（全文） | vBook |
|------|------|-----|-----------|-------|

**BookSemanticIndex**

- SectionNode：节树（title, summary, source）
- SlotProvenance：key* → primaryNodeId, role

### 8.2 每轮提问

```text
问句 → retrieve → compose → 运动脑 plans → 写信台
  → 网关拉 T → 编译 prompt → infer → pathMarker →（可选）accept
```

### 8.3 编译「前」vs「后」

| | 编译前 | 编译后 |
|--|--------|--------|
| 形态 | SlotProvenance 表：`h1…02 → n_ch3_s2` | prompt：`### 3.2 梦与象征` 下挂 key+text |
| 谁看 | 运动脑、retrieve、编目 UI | 主推理模型 |
| 关系 | 同数据两种视图；编译器负责展开 | |
